# 用户迁移与复制

「应用管理 → 用户迁移」（`/applications/user-transfer`）是独立的高级操作页面，用于将选中的终端账号从一个应用转移到另一个应用。应用所有者只能操作自己拥有的源、目标应用；管理员可以跨所有者操作，应用代理授权不等同于迁移权限。

## 操作步骤

1. 选择**源应用**和**目标应用**，二者不能相同。应用列表支持搜索与滚动加载。
2. 搜索并勾选源用户，支持用户名、昵称、邮箱、手机号和会员状态筛选，也可以开启「仅看已选」核对处理范围。筛选和翻页会保留勾选，每批最多 **100 位**；切换源应用会清空选择。
3. 选择「复制」或「迁移」，按需打开「强制覆盖」。默认是复制，强制覆盖默认关闭。
4. 点击「预检查」，查看每位用户的处理方式、冲突原因、设备限制和试用记录。此步骤不会修改账号。
5. 在确认弹窗勾选「我已确认上述范围」，确认恢复、覆盖或停用源账号的影响后执行。完成后让用户使用**目标应用的 App Key 和登录配置**重新登录。

## 复制、迁移与覆盖

| 选项 | 目标应用 | 源应用 |
| --- | --- | --- |
| 复制 | 新建账号或恢复已删除的唯一匹配账号，使用源账号资料、密码和会员到期时间 | 保持不变，原会话不受影响 |
| 迁移 | 新建账号或恢复已删除的唯一匹配账号，使用源账号资料、密码和会员到期时间 | 成功处理的源账号软删除、停止登录；提交后断开其 WS |
| 强制覆盖 | 仅覆盖唯一匹配的目标账号，保留其 ID、代理归属和历史数据；替换密码、资料、会员到期时间，并断开其 WS | 是否停用源账号仍取决于复制或迁移模式 |

会员到期时间是**替换，不是时长累加**。新建的目标账号不继承源代理归属，也不复制登录次数、IP、在线状态或会话。用户密码哈希只在后端内部复制，不会出现在迁移接口返回或批次记录中。

## 冲突处理

- **新建**：目标不存在身份冲突，创建账号。
- **跳过**：存在未删除的目标账号冲突，但未开启强制覆盖。跳过的源用户不会被删除。
- **覆盖**：开启强制覆盖，且用户名或邮箱只对应一个可确认身份的目标账号。
- **恢复**：唯一匹配的目标账号已逻辑删除，自动恢复原账号 ID，无需强制覆盖。密码、资料和会员到期时间按源账号替换；保留目标创建时间、代理归属、登录统计、历史数据、封禁和已领取试用限制。恢复增加有效用户数，同新建一样检查配额；同所有者迁移不会重复扣除注册配额。
- **阻止**：多账号匹配、用户名与邮箱交叉身份冲突、多个源用户指向同一个覆盖或恢复目标、源登录身份存在歧义。这些情况不自动清理历史，也不强行覆盖。

有「阻止」项时**整批不执行**。请返回取消勾选阻止项，或先修正数据再预检查。只有「跳过」项而没有可新建/覆盖/恢复项时，页面不允许提交执行。

## 设备、试用与历史数据

- 设备限制随账号复制，目标已有设备不删除。封禁取并集，正常源设备不能解除目标封禁。
- 设备记录转换为账号类型，不携带原卡密 ID、卡密设备权益、近期活跃信息或扩展 metadata。
- 已申请试用的记录保留。目标已有试用时不重新开始，到期时间只允许缩短、不允许延长。
- **订单、卡密、支付数据和登录历史不跨应用搬运**。源应用历史留在原处，便于审计；迁移不是整个应用的备份恢复。

## 配额与执行保障

复制新增账号，以及跨所有者迁移新增账号，需要目标所有者具备相应用户配额。同一所有者的应用间迁移不增加有效用户总量，不会在满额时额外扣除注册额度。覆盖已有目标账号不新增用户，也不消耗新增配额。

执行前会再次校验权限、配额和预检查快照。账号、设备、冲突或相关配置变化时，必须重新预检查。`previewToken` 绑定当前操作者、源和目标应用、模式、覆盖选项、所选用户及数据快照；执行时必须原样提交，不要自行生成或修改。该凭证不声明固定有效分钟数。成功批次记录唯一请求标识，重复提交会被拒绝。

普通冲突按预检查结果跳过，其余操作在同一数据库事务内执行：任一写入失败则回滚整批，不删除源账号，也不提前踢出 WS 会话。网络异常时不要连续重试执行，先刷新源、目标用户列表核对结果，再重新预检查。

## 管理接口

这些是后台管理接口，需要登录并拥有 `APP_USER_TRANSFER` 权限，不是第三方客户端的公开登录接口。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/app-user-transfers/applications` | 分页获取可操作应用 |
| GET | `/api/app-user-transfers/users` | 按 `appId` 分页获取源用户，可搜索用户名/邮箱 |
| POST | `/api/app-user-transfers/preview` | 只读预检查，返回处理列表和 `previewToken` |
| POST | `/api/app-user-transfers/execute` | 提交原预检查参数和 `previewToken` 执行批次 |

源用户列表支持 `keyword`（用户名/邮箱搜索）、`username`、`nickname`、`email`、`phone`、`memberStatus`（`ACTIVE` 未到期、`EXPIRED` 已到期、`NONE` 未开通）组合筛选，条件之间为 AND。可通过逗号分隔的 `userIds` 查看已选用户，最多 100 个有效 ID；仍只返回有权操作的源应用内未删除用户。筛选在后端执行，分页总数为筛选后的实际总数，响应不包含密码或密钥。

预检查请求示例（数字仅用于说明）：

```json
{
  "sourceAppId": 10,
  "targetAppId": 20,
  "mode": "COPY",
  "forceOverwrite": false,
  "userIds": [100, 101]
}
```

预检查和执行结果以 `RESTORE` 标记恢复项，并通过 `restoreCount` 单独统计；`createCount` 和 `overwriteCount` 不包含恢复项。批次审计表的 `overwrite_count` 统计复用目标行的总数（覆盖及恢复），具体动作记录在提交日志中。

执行时增加预检查返回的 `previewToken`，其余参数保持一致。未登录返回 HTTP 401，权限不足返回 HTTP 403，非法参数或不匹配的预检查凭证返回 HTTP 400。预检查接口返回结果不代表已经执行，应查看 `executed` 及逐项 `action`。

前后端应同时升级；后端通过 Flyway 迁移创建批次审计表、权限和菜单，仅替换前端不会生成菜单。

## 结果核验

- 按源、目标应用分别查询处理后的账号，核对用户名、邮箱、会员到期时间和设备封禁。
- 迁移模式下，成功处理的源账号不再出现在有效用户列表；跳过项保留。复制模式下源账号仍可使用。
- 用目标应用的登录配置验证账号；不要继续使用源应用的 App Key 判断目标账号是否可用。
- 覆盖或恢复会替换目标密码和会员配置；操作没有一键撤销入口。需要恢复时先核对批次记录及备份，避免覆盖后续业务变更。
